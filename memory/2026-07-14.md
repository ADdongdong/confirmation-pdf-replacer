# 2026-07-14 工作日志

## 函证PDF工具 - 白色覆盖区域坐标Bug修复

### 问题
用户反馈：上传PDF后拖动红色遮罩调整覆盖范围，输出结果未完全覆盖用户框选区域，
表格标题 "1. 本公司与贵公司的往来余额列示如下：" 仍然可见。

### 根因
`PdfProcessor.java` 第 233-240 行的 `Math.min` 比较混用了两套坐标系：

| 变量 | 坐标系 | 来源 |
|------|--------|------|
| `userWhiteoutBottom` | 布局坐标（从顶部算起） | 前端 `pct/100 * pageHeight` |
| `tableY` | PDF坐标（从底部算起） | `FormatExtractor` 用 `tp.getY()` 读取 |
| `tableY - 3` | 仍然是从底部算起 | 没转换就直接用了 |

例如：用户拖到 50% = 421pt (从顶部)，表格位于 397pt (从底部)：
- 错误：`Math.min(421, 394) = 394` 解释为从顶部 → 实际只覆盖到顶部 394pt
- 正确：`Math.min(421, pageHeight-tableY-3) = Math.min(421, 442) = 421` → 覆盖到顶部 421pt

导致白色覆盖区域比用户拖到的位置偏上 20-50pt，表格标题刚好漏出。

### 修复
将 `pageHeight` 提前获取，把 `tableY` 转换为从顶部算起的布局坐标后再做 `Math.min`：

```java
float pageHeight = page.getMediaBox().getHeight();
double maxWhiteoutFromTop = pageHeight - tableY - 3;  // 统一为从顶部算起
whiteoutBottom = Math.min(userWhiteoutBottom, maxWhiteoutFromTop);
```

### 验证
重新编译、重启服务，PID 27780 监听 8889 端口。
用户可在 http://localhost:8889 重新测试。

### 二次发现：前端 submitForm 也有 Bug
用户再次反馈"还是没变"，根因不是 Java 端，而是**前端 `index.html` 的 `submitForm`**：

```javascript
try {
  const resp = await fetch('/generate', { method: 'POST', body: formData });
  ...
} catch (err) {
  // 追加白化区域参数  ← 写在了 catch 里！
  if (previewData && previewData.userWhiteoutPercent != null) {
    var pdfBottomY = (previewData.userWhiteoutPercent / 100) * previewData.pageHeight;
    formData.append('whiteout_bottom', Math.round(pdfBottomY));
  }
}
```

只有当 fetch 失败时才会 append `whiteout_bottom` 参数，正常请求根本不会传这个参数。
所以后端 `req.whiteoutBottom` 一直为 null → 走自动检测路径 → 用户拖动完全无效。

**修复**：把 `formData.append('whiteout_bottom', ...)` 移到 fetch 调用之前的 try 块外。
变量名也改清楚了：`pdfBottomY` → `whiteoutTop`（因为这是从顶部算起的距离）。

### 教训
PDF 开发中坐标系极易出错：PDFBox 原生坐标是「左下角原点，Y 向上」，
而前端预览和业务布局通常用「左上角原点，Y 向下」。所有 `Math.min/max` 比较前
必须显式标注坐标系，或统一转换到同一坐标系。

**还要注意**：涉及多语言/多层调用栈的 bug，单端修复后必须验证另一端是否真的把数据传对。
上次只修了后端坐标系，没发现前端根本没传值，浪费了一轮交互。

## 加粗提示行重影 Bug 修复

### 问题
用户两次反馈"提示行重叠写了两次"（"若您方有相关本询证函函证事项问题..."）。

### 第一次尝试（失败）
改 `writeBoldText` 从「三重绘制 (x, x+0.4, x+0.8)」改为「两遍对称偏移 (x-0.35, x+0.35)」。
- 0.35pt 偏移在 10.5pt 字号下太小（≈0.47 像素），视觉上几乎不可见加粗效果
- 但对称偏移还是让两个字符之间有 0.7pt 间隙，产生了用户描述的"重叠写了两次"重影

### 第二次尝试（正确方案）
**改用真正的 SimSun Bold 字体 (`simsunb.ttf`)**，彻底抛弃伪加粗：

1. 新增 `findBoldFontFile()`：优先 `C:/Windows/Fonts/simsunb.ttf`，回退到 `simhei.ttf`
2. `process()` 加载两个字体：`font`（常规）+ `boldFont`（粗体）
3. `processPage` 接受两个字体参数
4. 循环中：`PDType0Font useFont = pt.bold ? boldFont : font; writeTextBlock(cs, useFont, pt, page);`
5. 删除整个 `writeBoldText` 方法

### 效果
- 标题"企业询证函"（18pt）：SimSun Bold 渲染，加粗效果真实
- 提示行（10.5pt）：SimSun Bold 渲染，单字符清晰无重影
- 一次绘制完成，无位置偏移

### 教训
"伪加粗"在中文宋体上不可行——任何非零偏移都会让字符边缘产生重影。
系统级 TrueType 字体（`C:\Windows\Fonts\simsunb.ttf`）几乎所有 Windows 都自带，
应该优先用真粗体字体而不是手工 hack。

## 关键发现：simsunb.ttf 的真身

`C:\Windows\Fonts\simsunb.ttf` 实际上**不是** SimSun Bold，而是 **SimSun-ExtB**（SimSun 扩展B区）！

- name 字段：`SimSun-ExtB`
- cmap：`{3 10}`（Format 4, segmented, Unicode BMP），但非常用字都没有
- 测试 `U+4F01`（企）：GID=0 ← **找不到字形**！
- 测试 `U+516C`（公）：GID=0 ← **找不到字形**！

PDFBox 加载后报 `No glyph for U+4F01 (企) in font SimSun-ExtB`，导致标题"企业询证函"完全写不进去。

**真正的"粗体"字体**：用 `C:\Windows\Fonts\simhei.ttf`（SimHei 黑体）：
- name：`SimHei`
- cmap：`{0 3}`（Format 0, Unicode BMP），包含完整常用汉字
- 测试 `U+4F01`（企）：GID=1335
- 测试 `U+516C`（公）：GID=1954

修正后的 `findBoldFontFile()` 优先级：`simhei.ttf` > `simfang.ttf` > `simsunb.ttf`（最后兜底）。
（兜底时打印警告，但不阻塞。）

### 教训
不要被 Windows 字体文件名误导。"simsunb" 字面看是 "SimSun Bold"，但微软实际上是把 SimSun-ExtB 独立成 ttf 文件的。判断一个字体能不能用，**必须用 PDFBox/fontbox 实际加载并测试常用字符的 GID**，不能只看文件名。

## 服务端后台中文乱码修复

### 问题
用户在 `start_server.bat` 启动的控制台看到一堆 `?` 乱码（"函证 PDF" → "���� PDF"）。

### 根因
两个独立问题叠加：
1. **`start_server.bat` 完全没有 `chcp 65001`** —— Windows cmd 默认代码页 936 (GBK)
2. **即使控制台是 65001，Java 的 `System.out.println` 默认按平台编码（GBK）写字节流**，
   `chcp 65001` 只影响 cmd 接收字节后**显示**时按 UTF-8 解码。两边编码不一致就是乱码。
3. 仅靠 `-Dfile.encoding=UTF-8` 还不够 —— 这只影响 Java 内部默认字符集，
   不影响 `System.out` 这个已经初始化好的 PrintStream。

### 修复（三处联动）

**1. `start_server.bat`**（原本最缺）：
```bat
chcp 65001 >nul
"%JAVA_HOME%\bin\java" -Xmx1024m -Dfile.encoding=UTF-8 -Dconsole.encoding=UTF-8 ^
  -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -cp "%CP%" com.hanzheng.WebServer
```

**2. `run.bat`**（原本有 chcp 但没 -D 参数）：
```bat
"%JAVA_HOME%\bin\java" -Xmx1024m -Dfile.encoding=UTF-8 -Dconsole.encoding=UTF-8 ^
  -Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8 -cp "..." com.hanzheng.WebServer
```

**3. `WebServer.java` main 开头**（最关键，把已经存在的 PrintStream 替换为 UTF-8）：
```java
public static void main(String[] args) throws Exception {
    // 强制 stdout/stderr 使用 UTF-8，避免 Windows 控制台（GBK）下中文乱码
    try {
        System.setOut(new PrintStream(System.out, true, "UTF-8"));
        System.setErr(new PrintStream(System.err, true, "UTF-8"));
    } catch (Exception e) {
        // 忽略
    }
    ...
}
```

### 编译命令（带 sourcepath）
```bash
javac -encoding UTF-8 -cp "lib/pdfbox-2.0.27.jar;lib/fontbox-2.0.27.jar;lib/commons-logging-1.2.jar" ^
  -sourcepath src/main/java -d target/classes src/main/java/com/hanzheng/WebServer.java
```

### 教训
Windows + JDK 1.8 + 中文日志三件套必须三管齐下：
1. 控制台代码页 65001
2. JVM 启动参数 `-Dfile.encoding=UTF-8`
3. **运行时强制重新包装 `System.out/err` 为 UTF-8 PrintStream**（最容易漏）
少任何一环都会出现 ???? 乱码。
